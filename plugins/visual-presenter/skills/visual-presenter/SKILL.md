# Visual-Presenter: 분석 결과 표현 스킬

problem-solver와 기획 스킬(P1~P6)이 낸 결과를 **표·도식·차트·한 장 요약·모션**으로 옮긴다.
내용을 새로 만들지 않는다. 받은 내용 중 무엇을 어떤 형식으로 보여 줄지만 정한다.

## 실행 통제 (공통)

- **범위 고정**: 요청 범위 그대로 산출. 단계·산출물 임의 추가 금지. 요청이 잘못됐으면 한 문장으로 지적한 뒤 요청대로 수행.
- **완료 정의**: Phase A에서 "무엇이 충족되면 이 단계가 끝인가"를 3줄 명시. 충족 시 추가 검증 라운드 없이 종료.
- **검증 원칙**: 결과 기준(전수 반영·커버리지·라벨 일관성·판정표)은 전량 유지 — 감사 대응 기록물. 절차적 재확인("다시 확인", "재검증 라운드")은 지시하지 않는다.
- **위임 상한**: 본 스킬의 「에이전트」는 역할 전환(내부 추론). 서브에이전트 스폰 금지, 검증 목적 위임 금지.
- **진행 보고**: 착수 1문장 / 진행 중에는 중요 발견·방향 전환·회귀 시에만 1~2문장 / 종료 시 결론 선행.
- **분량**: 규모 판정별 상한 준수. 필러 절·중복 요약·상투 문구 금지.
- **입력 점검**: Phase A에서 본문 「입력 점검표」를 대조한다. ① 대화·첨부·앞 단계 산출물에 이미 있는 항목은 다시 묻지 않는다 ② [필수]가 빠졌으면 실행 전에 빠진 항목만 1회 묶어서 묻는다 — 항목마다 '없으면 결과가 어떻게 달라지는지' 1줄을 붙이고, 빠진 [권장]도 같은 질문에 함께 싣는다 ③ [권장]만 빠졌으면 멈추지 않고 표의 '없을 때' 처리로 진행한다 — 승인 대기가 있는 규모에서는 계획과 함께 '있으면 정확도가 오르는 자료'로 1회 안내한다 ④ 사용자가 "없이 진행"을 지시하면 [가정]으로 채우고 결론에 '잠정'을 표기한다 ⑤ 산출물 첫머리에 입력 준비도(충분: 필수·권장 모두 확보 / 부분: 필수만 확보 / 부족: 필수가 빠진 채 진행), 입력 현황(확보·가정·미확보), '바뀌면 결론이 달라지는 입력' 상위 3개를 적는다.
- **민감정보**: 자료를 요청할 때 "개인정보·대외비는 가리고 올려 달라"를 1줄 고지한다. 입력에서 주민등록번호·환자정보·계좌번호 등을 발견하면 가린 뒤 처리하고 그 사실을 알린다. 외부 검색어에는 내부 안건명·금액·인명을 넣지 않고, 외부 모델에 넘길 자료는 기관명·인명을 일반화한다(금액은 구간·비율로).
- **최신 동향 탐색**: 본문 「최신 동향 탐색」 절과 references/frontier_scan.md에 따라 관련 신규 이론·연구·사례·제도를 1회 탐색해 반영한다. 실제로 연 출처만 싣고, 검색 수단이 없거나 생략했으면 그 사실을 적는다 — 기억으로 최신 동향을 지어내지 않는다.
- **표현**: 본문은 개조식과 표로 낸다. 도식·차트·한 장 요약·모션이 필요하거나 사용자가 시각화를 요청하면 visual-presenter 스킬로 넘긴다 (미설치 시 표와 개조식으로 대신하고 그 사실을 1줄 적는다).

## 입력 점검표 (Phase A에서 대조)

| 입력 | 구분 | 없을 때 | 산출에 미치는 영향 |
|---|:---:|---|---|
| 보여 줄 내용 — `[DATA]` 블록, 보고서 본문, 또는 표·수치 | 필수 | 질문 | 전체 (내용이 없으면 그리지 않는다) |
| 용도 — 결재·보고 / 발표 / 대외 공유 / 점검 화면 | 권장 | 결재·보고로 가정 [가정] | 스타일 추천안, 모션 모드 |
| 보여 줄 범위 — 전체 / 특정 부분 (예: 대안 비교만) | 권장 | 한 장 요약 + 핵심 도식 1~2개 [가정] | 그림 개수 |
| 조직 색 (주색·보조색) 또는 `[조직 프로필]` | 권장 | 중립 팔레트 | 색 |
| 스타일·모션 기법 지정 (예: "스위스 미니멀로", "키네틱 타이포로") | 선택 | Phase A에서 묻는다 | 스타일 방향, 모션 기법 |

- 수치·항목은 받은 내용에서만 가져온다. 그림에 필요한 값이 없으면 그 그림을 그리지 않고 "값 없음 — 생략"을 적는다.

## 최신 동향 탐색 (디자인 레퍼런스 — 요청 시에만)

- 내용에 관한 탐색은 하지 않는다. 앞 스킬의 탐색 결과(T번호·K번호)가 있으면 그대로 인용한다.
- 사용자가 "추천해줘", "요즘 방식으로", "레퍼런스 찾아줘", "새로운 방식 없나"라고 하면 **디자인 레퍼런스 탐색**을 한다.
  - 검색 2~4회. 대상은 디자인 매체, 수상작 모음, 작업물 공유 사이트(핀터레스트 등), 제작 기법 해설이다.
  - 검색어는 "내용 유형 + 형식 + 스타일어"로 쓴다 (예: "roadmap timeline motion design", "인포그래픽 한 장 요약 디자인"). 내부 안건명·기관명을 넣지 않는다.
  - 절차는 references/frontier_scan.md 3~4절을 따른다: 실제로 연 것만 싣고 링크를 단다.
  - 이미지를 직접 볼 수 없는 환경이면 그 사실을 밝히고, 설명 글을 근거로 추천한다. 사이트가 열리지 않으면 "열리지 않음"이라고 적는다.
  - 결과는 추천안 2~3개로 낸다: 방식 이름 / 어떤 내용에 맞는가 / 구현 등급(직접·근사·기획) / 참고 링크.
  - 참고한 작업물을 그대로 옮기지 않는다. 구성 원칙만 가져온다.
- 카탈로그에 없는 방식을 채택했으면 산출물 끝에 `○ 스킬 개선 후보`로 1줄 남긴다 (월간 점검에서 카탈로그에 넣을지 정한다).

## 워크플로우

### Phase A. 접수와 스타일 확인 [유일한 질문 지점]
1. 입력 점검표를 대조한다. [필수]가 없으면 그것을 묻고 멈춘다.
2. 환경을 확인한다: 그림을 낼 수 있는가(HTML·SVG 출력), 파일로 줄 수 있는가. 안 되면 표와 개조식만 내고 "도식 생략"을 1줄 적는다.
3. **생성 전에 스타일을 묻는다.** 질문은 1회, 아래를 한 번에 담는다.
   - 그릴 것: 형식 카드 번호와 그림마다의 메시지 한 줄
   - 스타일 방향: 다섯 가지를 한 줄씩 소개하고, 이 내용에 맞는 추천 1개와 이유를 붙인다. **여러 개를 골라도 된다**고 알린다.
   - 모션: 쓸지 여부. 쓴다면 references/motion_catalog.md에서 이 내용에 맞는 기법 후보 3개와 각각의 구현 등급을 제시한다. 여러 개를 골라도 된다.
   - 선택지를 눌러 고를 수 있는 환경이면 그 방식으로 묻는다.
4. 묻지 않고 진행하는 경우 — 추천안으로 진행하고 무엇을 골랐는지 첫 줄에 밝힌다.
   - 사용자가 이미 스타일·모션을 지정했다
   - 사용자가 "알아서", "추천대로"라고 했다
   - 사람이 응답할 수 없는 실행이다 (예약 작업, 다른 스킬이 넘긴 자동 실행)

### Phase B. 형식 고르기
1. 보여 줄 메시지를 그림마다 한 문장으로 쓴다. 이 문장이 그림의 제목이 된다.
2. references/pattern_cards.md에서 형식을 고른다. 내용 유형별 기본 배정은 아래 표를 따른다.
3. 단계별 상한: 기본 2~3개, 요청 시 늘린다. 표와 설명으로 충분한 내용은 그리지 않는다.

| 내용 | 형식 카드 |
|---|---|
| 이슈 구조 (problem-solver 01) | 1A 가로 트리 / 1B 세로 트리 |
| 대안 평가 (04) | 2A 점수 히트맵 / 2B 점 비교 |
| SWOT (P1) | 3A 4분면 카드 / 3B 교차 전략표 |
| 전략맵·목표 체계 (P2) | 4A 관점 층 + 화살표 / 4B 계층 목록 |
| 과제 포트폴리오 (P3) | 5A 2×2 버블 |
| 리스크 판정 (P4, 06) | 6A 5×5 매트릭스 + 근거 표 |
| 로드맵 (P5, 05) | 7A 간트 / 7B 지금·다음·이후 |
| 역할·의존관계 (P5) | 8A RACI / 8B 선후 흐름도 |
| 점검·환류 (P6) | 9B 지표 대시보드 |
| 한 장 요약 (공통) | 10A 수치 강조 인포그래픽 |

### Phase C. 스타일 입히기
references/style_cards.md에서 사용자가 고른 방향의 규칙을 적용한다.

- **하나를 골랐을 때**: 산출물 전체에 그 방향을 쓴다.
- **여러 개를 골랐을 때**: 어떻게 쓸지 사용자의 말에서 읽는다. 말이 없으면 '시안 비교'로 한다.
  - 시안 비교: 같은 그림(한 장 요약 또는 핵심 도식 1개)을 방향별로 그려 나란히 보여 준다. 고른 뒤 나머지를 그 방향으로 완성한다.
  - 그림별 배정: 그림마다 다른 방향을 쓴다. 한 그림 안에서는 한 방향만 쓴다.
- 방향을 섞어 한 그림을 만들지 않는다. 섞고 싶다는 요청이면 어느 방향의 무엇(색·글자·도형)을 가져올지 확인한다.

#### 추천 기준 (추천안을 고를 때만 쓴다 — 강제가 아니다)
| 내용·용도 | 추천 방향 | 이유 |
|---|---|---|
| 결재·보고 문서의 본문 도식 | D 스위스 미니멀 | 장식이 없어 인쇄와 흑백에서도 읽힌다 |
| 한 장 요약, 핵심 메시지 차트 | B 에디토리얼 그래픽 | 메시지가 제목으로 먼저 읽힌다 |
| 점검 화면, 발표용 대시보드 | E 다크 테크 | 수치와 추이가 화면에서 도드라진다 |
| 대외 공유, 교육, 낯선 개념 설명 | F 일러스트 설명형 | 비유로 진입 장벽을 낮춘다 |
| 사람·사례·맥락이 중요한 데이터 | A 데이터 휴머니즘 | 평균 뒤의 개별 차이를 보여 준다 |

- 사용자의 선택이 추천과 달라도 그대로 따른다. 읽기 어려워지는 조합이면(예: 인쇄용에 어두운 바탕) 1줄로 알리고 진행한다.

### Phase D. 모션 (선택했을 때)
- 사용자가 모션을 골랐을 때만 references/motion.md와 references/motion_catalog.md를 로드해 적용한다.
- 카탈로그의 기법을 폭넓게 쓴다. 같은 기법만 반복하지 않고, 내용에 맞는 기법을 고른다.
- 기법마다 구현 등급이 있다. **직접**은 바로 만들고, **근사**는 비슷하게 만들되 한계를 1줄 알리고, **기획**은 만들 수 없음을 밝히고 구성안(장면·문장·기법)만 낸다.
- 결재·인쇄용 산출물에는 모션을 넣지 않고 마지막 정지 화면을 낸다.

### Phase E. 산출
- 형식: 단일 파일 HTML(그림은 인라인 SVG)을 기본으로 한다. 외부 자원을 불러오지 않는다. 채팅 안에서 그림을 바로 보여 줄 수 있으면 그렇게 한다.
- 구성: 그림마다 **메시지 제목 → 그림 → 읽는 법 1~2줄 → 출처(어느 블록·어느 절)** 순서로 둔다.
- 글 버전: 그림과 같은 내용을 개조식으로 함께 낸다. 그림은 추가이지 대체가 아니다.
- 모바일 폭에서 읽히는지, 밝은 화면과 어두운 화면에서 글자가 보이는지 확인한다.

#### 출력 전 점검 (6개)
1. 그림의 모든 수치·항목이 받은 내용에 있는가
2. 제목이 형식 이름이 아니라 메시지인가
3. 범례 없이 직접 라벨로 읽히는가
4. 색을 빼도 의미가 구분되는가 (글자·기호 병기)
5. 한 그림의 계열·범주가 4개 안팎인가
6. 글 버전이 함께 있는가

## 경계

- 분석·판단·수치 산출은 하지 않는다. 내용이 부족하면 해당 분석 스킬로 돌려보낸다.
- 받은 결론을 바꾸지 않는다. 그림에서 결론과 다른 인상이 생기면 그 그림을 고친다.
- 슬라이드 파일(PPT)이나 문서 파일이 필요하면 그 형식의 전용 스킬을 쓴다.

## 공통 금지 사항

- 그림을 채우려고 수치·항목을 만들지 않는다
- 근거 없는 위치 찍기 금지 (점수 출처가 없는 2×2, 매트릭스)
- 입체 효과·그림자·장식용 아이콘으로 빈 곳을 채우지 않는다
- 확정되지 않은 일정을 간트로 그려 확정처럼 보이게 하지 않는다
- 특정 작품·브랜드의 디자인을 그대로 옮기지 않는다
